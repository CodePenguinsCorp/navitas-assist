# NAV-31 — Editor de workflows de RMA

## Objetivo e escopo

Administradores configuram status e transições sem implantação. Operadores usam a mesma regra pelo Kanban, formulário e lote. Rascunhos não afetam a operação; a publicação cria uma versão imutável para auditoria.

Branch autorizada pelo usuário: `NAV-31-Criar-editor-de-workflows-status-e-transições-do-RMA`, base `548ff79`. A NAV-34 segue em PR separado; não incorporar seu commit. Reservar `V3__configure_rma_workflows.sql`, evitando o V2 da NAV-34.

## Decisões de implementação

- Substituir status persistidos como enums por códigos estáveis de até 60 caracteres. Manter `RmaStatus` como enum dos estágios operacionais de SLA. Status configurados possuem nome, categoria, ordenação, atividade e estágio de SLA. Os códigos atuais permanecem válidos.
- Um workflow global inicial, seguindo o produto atual. Sem múltiplos quadros/workflows nesta issue. Documento JSON tipado persistido em uma linha de configuração com lock de escrita; nenhuma expressão arbitrária ou código executável.
- Configuração inicial preserva o comportamento atual: nove status e transições entre quaisquer status distintos, para ADMIN, SERVICE_DESK e TECHNICIAN. VIEWER não transiciona.
- Categorias: `PENDING`, `IN_PROGRESS`, `DONE`. Categoria DONE encerra SLA. Os demais status escolhem um dos seis estágios ativos atuais para reutilizar sua política de SLA.
- Ordem dos status vem da ordem do array. Arquivar define `active=false`: não aceita novas entradas, mas permanece visível enquanto houver RMAs e permite saída para um status ativo. Não excluir status atualmente usado por RMA. Códigos publicados não podem ser renomeados silenciosamente.
- Publicar valida códigos/nomes únicos, inicial ativo não terminal, destinos existentes e ativos, papéis, campos/ações permitidos, regras contraditórias e possibilidade de chegar a um estado DONE. Status ativos não terminais não podem ficar sem saída. Regras são validadas novamente no backend a cada transição.
- Preservar nome do status, nome do workflow e número da versão em cada evento de histórico. Renomeações posteriores não alteram esses eventos. Registros existentes recebem snapshots da configuração inicial.
- A pedido do usuário, criar módulos próprios de checklist e aprovação na NAV-61, atribuída a André e relacionada à NAV-31. NAV-31 apenas consulta essas fontes; não aceita flags de aprovação/conclusão enviadas pelo cliente. A relação com outro RMA pertence à NAV-31 e exige nota, autor e data.
- Ações pós-transição limitadas a adicionar nota, definir prioridade e remover responsável, com auditoria existente; tudo participa da mesma transação.
- Escritas de workflow, criação de RMA e transições adquirem primeiro o lock da configuração; edições comuns e operações NAV-61 adquirem lock do RMA. Nenhuma operação que já segura lock de RMA solicita o lock de configuração. Atualizações de rascunho e publicação exigem revisão esperada, evitando sobrescrita entre administradores.

## Contrato HTTP compartilhado

Tipos, nomes e valores desta seção vinculam backend e frontend.

```ts
type WorkflowCategory = 'PENDING' | 'IN_PROGRESS' | 'DONE';
type WorkflowSlaStage = 'RECEIVED' | 'TRIAGE' | 'IN_DIAGNOSIS' | 'WAITING_PART' | 'IN_REPAIR' | 'IN_TESTS';
interface WorkflowStatusDefinition { code: string; label: string; category: WorkflowCategory; active: boolean; slaStage: WorkflowSlaStage | null }
interface WorkflowCondition { type: 'FIELD' | 'CHECKLIST' | 'APPROVAL' | 'RELATED_STATUS'; field: string | null; operator: 'PRESENT' | 'EQUALS' | 'NOT_EQUALS'; value: string | null }
interface WorkflowAction { type: 'ADD_NOTE' | 'SET_PRIORITY' | 'CLEAR_ASSIGNEE'; value: string | null }
interface WorkflowTransitionDefinition { from: string; to: string; roles: UserRole[]; requiredFields: string[]; conditions: WorkflowCondition[]; actions: WorkflowAction[] }
interface WorkflowDefinition { name: string; initialStatus: string; statuses: WorkflowStatusDefinition[]; transitions: WorkflowTransitionDefinition[] }
interface PublishedWorkflow { version: number; definition: WorkflowDefinition }
interface WorkflowDraft { publishedVersion: number; revision: number; definition: WorkflowDefinition | null }
interface WorkflowTransitionOption { status: string; label: string; allowed: boolean; reason: string | null }
interface RelatedRmaRequest { relatedRmaId: number | null; note: string; expectedUpdatedAt?: string | null }
```

- `GET /api/workflows`: PublishedWorkflow, qualquer autenticado.
- `GET /api/workflows/draft`: WorkflowDraft, ADMIN.
- `POST /api/workflows/draft` (corpo `{}`): inicia cópia do publicado ou retorna rascunho existente; WorkflowDraft, ADMIN.
- `PUT /api/workflows/draft`: `{expectedRevision, definition}`; retorna WorkflowDraft, ADMIN. Salvar pode conter configuração incompleta editável; rejeitar estruturas/tamanhos malformados. Validação operacional completa ocorre ao publicar.
- `DELETE /api/workflows/draft?revision=N`: descarta somente o rascunho; retorna 204, ADMIN.
- `POST /api/workflows/publish`: `{expectedRevision}`; retorna PublishedWorkflow, ADMIN.
- `PATCH /api/rmas/{id}/related-rma`: RelatedRmaRequest; retorna RmaResponse. ADMIN/SERVICE_DESK/TECHNICIAN.
- RmaResponse mantém `status` string e acrescenta `statusLabel`, `statusCategory`, `workflowVersion`, `transitionOptions: WorkflowTransitionOption[]`, `relatedRmaId: number | null`.
- RmaStatusHistoryResponse mantém campos e acrescenta `statusLabel`, `workflowName`, `workflowVersion`.
- RmaStatusUpdateRequest e RmaBulkStatusUpdateRequest passam a códigos string, aceitam opcionalmente `expectedWorkflowVersion`; status esperado no lote continua obrigatório. Request individual também aceita `expectedStatus`, sempre enviado pelo frontend. Versão/status obsoletos são recusados, não sobrescritos.
- Respostas de erro seguem ApiError existente (400 regras/validação/conflito, 403 perfil, 404 recurso). Sem expor entidades ou senhas.
- Campos permitidos em requiredFields/condições FIELD: `invoiceNumber`, `reportedFailure`, `receivedAccessories`, `physicalCondition`, `repairSummary`, `replacedPartsSummary`, `testSummary`, `assigneeId`, `diagnosis.foundFailure`, `diagnosis.technicianName`, `trackingCode`, `carrier`, `shippedAt`, `purchaseDate`, `priority`.
- CHECKLIST usa `field` como código de modelo NAV-61 e EQUALS/NOT_EQUALS com `value` `true`/`false`; consulta a execução mais recente daquele modelo no RMA, sem execução significa false. APPROVAL usa `field` como finalidade/código de solicitação NAV-61 e o mesmo valor/operador; consulta a solicitação mais recente para o código (APPROVED=true; PENDING/REJECTED/ausente=false). RELATED_STATUS usa value como código do status do RMA relacionado. FIELD PRESENT dispensa value.
- Códigos de checklist inexistentes, auto-relacionamento e referência inexistente são recusados. Publicação exige modelos referenciados existentes e ativos. Arquivar modelo ainda referenciado pelo workflow publicado é recusado; retirar a condição e publicar antes do arquivamento. Referência somente em rascunho não impede arquivar, mas bloqueará sua publicação. Criação/edição de modelos toma lock de configuração antes do modelo para serializar arquivamento/publicação. Arquivar status no editor remove entradas para ele; manter saídas para migração de cards arquivados.

## NAV-61 — módulos operacionais e contrato

Sem modelos de protocolo com medições (NAV-45) ou cálculos/alçadas financeiras (NAV-39). Esta entrega cria a base versionada de checklist e o ciclo de solicitação/decisão interna usado pela NAV-31.

```ts
interface ChecklistItemDefinition { code: string; label: string; required: boolean }
interface ChecklistTemplateRequest { code: string; name: string; items: ChecklistItemDefinition[]; active: boolean; expectedVersion?: number }
interface ChecklistTemplate { id: number; code: string; name: string; items: ChecklistItemDefinition[]; active: boolean; version: number }
interface RmaChecklistItem extends ChecklistItemDefinition { checked: boolean; note: string | null; updatedBy: string | null; updatedAt: string | null }
interface ChecklistAuditEvent { itemCode: string | null; checked: boolean | null; note: string; actor: string; at: string }
interface RmaChecklistExecution { id: number; templateCode: string; templateName: string; templateVersion: number; items: RmaChecklistItem[]; completed: boolean; revision: number; history: ChecklistAuditEvent[] }
interface ChecklistItemUpdateRequest { checked: boolean; note: string; expectedRevision: number }
interface RmaApproval { id: number; code: string; justification: string; status: 'PENDING' | 'APPROVED' | 'REJECTED'; requestedBy: string; requestedAt: string; decidedBy: string | null; decidedAt: string | null; decisionNote: string | null; revision: number }
```

- `GET /api/checklist-templates`: ChecklistTemplate[], autenticados.
- `POST /api/checklist-templates`: ChecklistTemplateRequest; retorna ChecklistTemplate (201), ADMIN.
- `PUT /api/checklist-templates/{id}`: ChecklistTemplateRequest com expectedVersion obrigatório; retorna ChecklistTemplate, ADMIN. Código imutável; alteração gera próxima versão, arquivamento preserva modelo e execuções.
- `GET /api/rmas/{id}/checklists`: RmaChecklistExecution[], autenticados.
- `POST /api/rmas/{id}/checklists`: `{templateId}`; retorna execução com snapshot da versão (201), ADMIN/SERVICE_DESK/TECHNICIAN. Reiniciar gera nova execução, preservando anteriores.
- `PATCH /api/rmas/{id}/checklists/{executionId}/items/{itemCode}`: ChecklistItemUpdateRequest; retorna execução atualizada, ADMIN/SERVICE_DESK/TECHNICIAN. Validar propriedade do RMA, revisão, item, nota obrigatória e modelo original do snapshot. Cada mudança gera evento; completo significa todos os itens obrigatórios marcados. Modelos têm ao menos um item obrigatório.
- `GET /api/rmas/{id}/approvals`: RmaApproval[], autenticados.
- `POST /api/rmas/{id}/approvals`: `{code,justification}`; retorna PENDING (201), ADMIN/SERVICE_DESK/TECHNICIAN. Solicitação mais recente suplanta decisões anteriores para a condição, preservando todo o histórico.
- `PATCH /api/rmas/{id}/approvals/{approvalId}`: `{status:'APPROVED'|'REJECTED',note,expectedRevision}`; retorna decisão, ADMIN/SERVICE_DESK. Exigir nota, revisão e estado PENDING. Não aceitar segunda decisão nem decidir solicitação que já foi substituída por outra do mesmo código.
- Persistência separada com FKs de propriedade do RMA e exclusão em cascata para testes/limpeza; sem novo endpoint de exclusão de RMA. Versionamento de modelos e execuções via revisão; serializar operações por RMA com a transição para não ler evidência intermediária.
- UI: ADMIN `/checklists` para modelos; painel operacional nos detalhes do RMA para vincular/reiniciar checklist, executar itens, consultar histórico e solicitar/decidir aprovações. Somente perfis autorizados veem ações.

Diagrama SVG de saída do status selecionado, navegável por status e acessível por teclado; evitar biblioteca gráfica e editor JSON.

Formulário de status e lote usam regras retornadas pela API (interseção dos destinos permitidos no lote); revalidação no backend trata alterações concorrentes. Status arquivados em uso continuam acessíveis para consulta e migração.
